Proposal · bitplan.dev · 2026-08-28

BitPlan: plan documents on the chain, not on a server

Every plan an agent publishes through postplan.dev lands on someone else's Postgres and S3. That company can read, alter, lose, or be compelled to hand over every draft. BitPlan removes the host: the CLI inscribes the document as a 1Sat Ordinal on BSV, each revision is a reinscription on the same coin, and bitplan.dev is only a viewer with no storage of its own.

Removing the host inverts the risk. PostPlan's worst case: one company reads your plan. BitPlan's worst case: everyone reads it, forever — a published transaction cannot be deleted or amended. So BitPlan encrypts by default, and the six choices that shape the security model are now decided — recorded below with the full option space they were chosen from.

Architecture

Publishing a version

  1. Validate. Same parse5 policy as PostPlan: no external scripts, no forms, no iframes. Fails locally before anything touches the network.
  2. Scan for secrets. Gitleaks-style patterns (API keys, private keys, connection strings) plus local filesystem paths. A hit blocks publish until the user overrides per-finding. This runs even for encrypted publishes — see the security model for why.
  3. Show the bill and the warning. Byte count, fee estimate, and one sentence: "This is permanent. It cannot be deleted." Confirm.
  4. Encrypt (default). Fresh random 32-byte key per draft; AES-256-GCM over the HTML; the content key is wrapped according to Decision 1.
  5. Inscribe or reinscribe. First publish calls inscribe → the ordinal's origin outpoint becomes the permanent draft ID. Later publishes spend the current coin into a new output with a new inscription envelope — one transaction per version.
  6. Record locally. ~/.bitplan/drafts.json maps file path → origin, exactly like PostPlan maps file path → draft id.

Versioning: one coin, many inscriptions

The draft is the coin. Every version is a spend of that same satoshi carrying new content. The chain itself is the version history — ordered, timestamped, and signed by the publishing key. Nothing to store server-side.

Reading

bitplan.dev is a static site. It resolves /d/<origin> through a public indexer to the newest inscription in the chain, fetches the bytes, and — if the draft is encrypted — decrypts in the browser using a key that never reaches any server. Agents use bitplan fetch <url>, which does the same thing over HTTP and prints the HTML. The CSP story matches PostPlan: the viewer renders the document with script-src 'none'.

What auth becomes

PostPlan needs Shoo + API keys because a server must decide who may write to a draft. BitPlan has no server to convince: only the holder of the coin can spend it, so only the holder can publish a new version. The wallet is the account, the signature is the API key, and ownership transfers are a coin send. bitplan list reads the wallet's ordinals basket filtered to app=bitplan — no /api/drafts endpoint required. Optional BAP identity signing (signWithBAP, already in the SDK) adds public attribution when wanted.

Devices, revocation, rotation — where PostPlan's model maps worst

PostPlan's /cli/auth page mints one API key per device and lets you revoke each individually; revoking one stops that machine while your account and other devices continue. BitPlan has no server to honor a revocation list, so the mapping is different — better in one way, worse in two:

OperationPostPlanBitPlan
Revoke a deviceServer marks the key revoked_at; works if the operator is honest and upRotate: one batch transaction sweeps every draft coin to a fresh key (SDK sweep machinery exists). The old key holds nothing, so it can publish nothing — enforced by consensus, no server involved. Stronger guarantee, ~one tx of cost.
Damage before you noticeAttacker publishes junk versions; operator can retroactively disable a draft (disabled_at in the schema)Attacker can publish junk versions or transfer draft coins away. A junk version can be superseded by your next publish, never erased from the history chain. A stolen coin is gone unless returned.
Stop future readsRevoked key can no longer call the APIno analogue The attacker keeps the public ciphertext and the old key forever: every draft wrapped to the compromised key stays decryptable by them permanently. Rotation protects future drafts only. This is the sharpest difference in the whole design — key hygiene matters more here than on PostPlan.
Several devices, one accountThree CLIs, three keys, one account — nativeA draft coin lives on exactly one key. Per-device wallets = per-device draft ownership (drafts transferable between devices, not shared). A shared seed gives every device access but removes per-device revocation. The SDK's cosign machinery is a plausible v2 path to true multi-device, at the cost of a coordinator. Open question below.

Security model

Encrypted by default is decided. Here is exactly what that does and does not buy, in plain terms:

ThreatCovered?Plain English
Host reads your planseliminatedThere is no host. Nobody operates a database of your documents.
Host loses / censors your planseliminatedAnyone can run an indexer; the data outlives bitplan.dev itself.
Public reads an encrypted planprotectedThey see ciphertext and a size. AES-256-GCM with a random per-draft key.
Accidental cleartext publishmitigatedEncrypted default + secret scan + typed confirmation. But if it happens, it is permanent. This is the single worst failure mode of the product.
Leaked share linkdepends on Decision 1If the key travels in the link, anyone who ever obtains the link can decrypt that draft forever. There is no revocation on an immutable ledger.
Search engines index your planfixed for encrypted tiersPostPlan today: no robots.txt, no noindex — a URL shared in a public PR can be crawled and indexed (the Claude Artifacts failure). BitPlan: the viewer ships robots.txt + X-Robots-Tag: noindex on draft routes, and for encrypted drafts a crawler that ignores both still only fetches ciphertext — the key lives in the URL fragment, which browsers never transmit. Cleartext drafts remain crawlable via the chain itself; no viewer header can change that.
Metadata leakagedepends on Decision 2Even with encrypted content, cleartext MAP fields (title, repo name, git branch) can leak what you're working on. Sizes and timestamps always leak.
Harvest now, decrypt lateraccepted risksecp256k1 ECDH and AES are not post-quantum. Ciphertext is public forever, so a future quantum computer could decrypt today's drafts. Plan documents usually have a shelf life of months; judge accordingly, and never publish long-lived secrets even encrypted — that is why the secret scan always runs.
Lost wallet / lost keyuser's burdenNo password reset exists. Losing the decryption key means the ciphertext on chain is unreadable forever. Mitigation: the SDK's existing BAP/wallet backup flows, plus Decision 1's recovery wrap.
Stolen device / compromised publishing keyrotation, with a sharp edgeThe "revoke" analogue is rotating: one batch transaction sweeps every draft coin to a fresh key, and the old key can publish nothing — enforced by consensus, not by a server. But rotation protects the future only: the attacker holds the public ciphertext plus the old key, so every draft wrapped to that key is decryptable by them forever. And a malicious version they published before rotation can be superseded by your next version, never erased. See "Devices, revocation, rotation" below.
The rule the tooling enforces: treat the chain like a newspaper, even when encrypting. Encryption sets the reading cost; it does not restore the delete button. The secret scanner therefore blocks credentials and personal data on every publish, encrypted or not.

The three visibility tiers

PostPlan and Claude Artifacts both really offer one tier: unlisted — public content behind an unguessable URL. A public ledger cannot copy that trick: URLs guard nothing when anyone can enumerate every inscription tagged app=bitplan with a chain scanner. What replaces it is cleaner, because each tier is enforced by cryptography rather than by hoping a URL stays secret:

TierMechanismWho can readPostPlan equivalent
PublicCleartext inscriptionEveryone, including chain scanners and search engines. More exposed than a PostPlan draft — it is listed, not unlisted, and permanent.None — PostPlan has no truly listed tier
UnlistedCiphertext on chain; key rides in the link fragment (#k=…)Anyone holding the link — humans and agents alike, pasted in a PR like today. Fragments never reach servers, logs, or crawlers, so the secret sits in a strictly safer channel than PostPlan's URL path.The normal PostPlan draft, done correctly
PrivateCiphertext on chain; content key wrapped to named recipients — a wallet public key, or a BAP identity resolved through Sigma IdentityExactly the people you name. No server grants or revokes access; the wrap is the ACL.None — PostPlan cannot do this at all

Sigma auth's role here is deliberately narrow: with no server hosting content, there is no place to enforce a login wall. Sigma Identity instead serves as the directory — "share with @satchmo" resolves a BAP ID to its current public key, and the CLI wraps the content key to it. The reader proves identity to no one; they simply hold the only key that opens the wrap. The viewer can still use Sigma auth as a convenience login to locate your wallet key in a browser, but it is never the thing standing between an attacker and the plaintext.

The bitplan.dev viewer additionally ships what PostPlan forgot on day one: robots.txt disallowing draft routes and X-Robots-Tag: noindex on every draft response. For encrypted tiers that is defense in depth; for the public tier it is honest-but-limited — the chain itself remains crawlable, which is exactly why cleartext requires Decision 6's gate.

DECISION 1 · the big one ✓ DECIDED — A: wallet-wrapped; share to known pubkeys (BRC-2)

How do decryption keys travel?

Every encrypted draft has one content key. Where that key lives determines who can read the plan, how sharing feels, and what happens when things leak.

DECISION 2 ✓ DECIDED — A: minimal on chain

What stays readable on chain when a draft is encrypted?

PostPlan's dashboard earns its keep from metadata: drafts grouped by auto-linked git repo (with a GitHub link), and every version row showing the commit subject, branch + short sha, a dirty badge when the tree had uncommitted changes, and publish time. BitPlan keeps that experience — the question is where the metadata lives. On chain in cleartext MAP fields it is public forever; inside the encrypted payload it is visible only after decryption.

DECISION 3 ✓ DECIDED — B first: external BRC-100 wallet only; C is a follow-up

Which wallet does the CLI use?

The architecture question is already settled by a standard: the CLI codes against the BRC-100 wallet interface once, and every option below is a configuration of which wallet answers. Verified in source: BSV Desktop serves the full BRC-100 API (createAction, encrypt, decrypt, getPublicKey, …) on 127.0.0.1:3321 with per-origin permission prompts in the wallet UI, and @1sat/wallet is a BRC-100 engine. Two properties fall out for free: the wallet itself asks before each publish spend (a second human gate), and encrypted drafts open with any compliant wallet holding the key — not just our tooling.

What a version costs

A 50 KB encrypted plan ≈ 51 KB transaction. At the common 1 sat/KB miner rate and BSV at $16.58: ≈ 51 sats ≈ $0.00085. Twenty versions of a large plan: about two cents. Numbers marked approximate — miner fee policy needs a live check during Phase 1, and the CLI always shows the real fee before you confirm.

Follow-up issues (deliberately out of v1)

  • Embedded wallet + auto-detect (D3 → C): @1sat/wallet-node fallback when no bridge answers, for npx strangers and CI. Ships only after the pure-client path is solid.
  • Unlisted link-key tier (D1 expansion): fragment-key share links for the PR-paste workflow, added as an explicit per-share choice on top of wallet wraps.
  • Public cleartext tier (D6 → B): --public + secret scan + typed confirmation, once the encrypted product has proven the pipeline.
  • Rich local dashboard cache (D2 comfort): optional local metadata cache for instant repo-grouped list on fresh machines.

Open questions (not blocking the decisions above)

  • Draft transfer & multi-author: the coin model gives single-writer semantics; co-authoring means passing the coin or multisig. Punt to v2?
  • Multi-device publishing: largely dissolved by D3-B — BSV Desktop builds on @bsv/wallet-toolbox, whose storage can be remote and shared across devices (StorageClient), so device sync is the wallet's job, not BitPlan's. Residual: confirm shared-storage UX during Phase 1 testing.
  • BAP attribution default: sign versions with a public identity, or stay pseudonymous by default? Interacts with Decision 2.
  • Anonymous/free tier: PostPlan allows unauthenticated uploads. On-chain publishing always costs sats — is a faucet-funded first draft worth it for onboarding?
  • Name/discovery: OpNS names for pretty URLs (bitplan.dev/@satchmo/roadmap) — v2 candidate, machinery exists in the SDK.
