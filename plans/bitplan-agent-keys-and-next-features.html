BitPlan · draft 6 · 2026-09-02

One envelope, links, folders, hosted drafts

Five small steps that let anyone use BitPlan, with or without Bitcoin, let a plan be a whole folder, and settle what a plan is allowed to do in the browser.

What changed since draft 5

  • The copy button now works inside the viewer. The viewer runs plans with scripts on and network off, and the button falls back through three copy methods. This plan is built from the new template in docs/templates/plan.html.
  • Inscribe writes only the latest draft by default. Full history is a flag.

Where we landed

  • Agents use your wallet. When you are driving an agent, it publishes as you. No second key, nothing to fund, nothing to lose. A separate agent identity is only for jobs that run with nobody present, and that is a later item.
  • One envelope. There were two encrypted formats, one for private plans and one for shared plans. A private plan is just a shared plan with one reader, so the private format goes away. It is called the bitplan envelope. No version numbers in its name.
  • Links need no new format. A reader link is a throwaway key. Its public half is a normal reader entry in the envelope. Its private half rides in the link. The bytes on chain look exactly like a plan shared with one more person.
  • Hosted drafts are a go. The same encrypted envelope stored by bitplan.dev instead of the chain, so people with no Bitcoin can use BitPlan. Moving a hosted draft to the chain is called inscribe.
  • Handing a plan to another person already works with 1sat ordinals send. No BitPlan command needed.
  • A plan can be a folder. The envelope encrypts bytes, so a folder packed into one bundle is the same envelope, one transaction per version, same readers. Diagrams, images, fonts, a built React app. No new on-chain format needed.
  • External images are fine. Most will be on-chain assets served from ORDFS gateways such as api.1sat.app, which are immutable and cheap. A plan may reference them directly. The trade-off, stated once: a reference to a host you do not control can tell that host when the plan was opened.
  • Hosting has a cost line. Storing folders and images for hosted drafts is where free ends and paid begins. Chain publishing stays pay-per-byte.
  • Cut for now: Secure Enclave policies, a headless wallet daemon, signed version lists, a wallet-signed account system, a new viewer route, plugin manifests for four editors. Each has a Linear issue if it comes back.

The five steps

1. One envelope

CLI and viewer · about two days · no wallet changes

Stop writing the private format. Every new plan is the shared layout with the publisher as the only reader. Delete the private read path too. The three private plans that exist were never shared and can be republished. The version byte on the wire stays what it is, because changing it is work that buys nothing. Docs say "the bitplan envelope" and nothing else.

Done when: the CLI has one encrypt path, the viewer has one decrypt path, and the envelope spec page describes one format.

2. Links for readers

CLI and viewer · about two days · no envelope changes

Today a reader needs a wallet. Every competitor can hand someone a link. With bitplan upload plan.html --link the CLI makes a throwaway key pair, adds its public half as a reader, and prints a URL whose fragment holds the private half. The fragment never leaves the browser. The viewer sees the fragment, rebuilds the key, and decrypts the way any reader's wallet would, using the decrypt code already in the installed SDK.

Anyone with the link can read. The CLI says so when it prints one. To cut off a leaked link, publish the next version with --private. The link secret is random and unrelated to any wallet key, so a leaked link exposes the plan and nothing else. Links also work inside browsers that block wallets, such as the one in the Claude desktop app.

Done when: a plan opens in a private browser window from the link alone, the same link opens the next version, and one test opens a CLI-written link envelope in the web implementation.

3. A plan can be a folder

CLI and viewer · about three days · no envelope changes

bitplan upload ./plan/ packs the folder into one bundle, a small index plus the files, and encrypts it exactly like a single file. The viewer decrypts, unpacks in memory, and hands the files to the frame by rewriting relative paths to in-memory URLs. Images, SVG, CSS, fonts, and a Vite build with one script bundle all resolve. Versioning does not change: a new version is the whole bundle again.

Two things this deliberately does not do yet. It does not give a plan a real URL space, so module imports and relative fetches inside a compiled app need the per-plan origin described under "Later". And it re-uploads unchanged files on every version. ORDFS directories, once 1sat-sdk can write them, are the way to reference unchanged files across versions and keep drafts lean. Not required for encrypted plans, so not on the critical path.

Done when: a folder with an image and a stylesheet opens in the viewer with both showing, and a 2 MB Vite build opens with its script running when scripts are on.

4. Hosted drafts and inscribe

Web and CLI · about a week · needs step 2 for the no-wallet case

bitplan upload plan.html --hosted stores the encrypted envelope on bitplan.dev and prints a link. Updating it is the same command again. The server holds ciphertext and a per-draft secret the CLI keeps in its local drafts map, the same idea postplan uses. No accounts, no sign-in, no wallet needed to publish or read when combined with a reader link. When a wallet is present, the plan is also encrypted to it, so it can be inscribed later.

bitplan inscribe h_xxxx puts the draft on the chain. Hosted versions are not transactions, so the on-chain origin does not exist until this moment. The hosted link must redirect to the chain forever after. By default inscribe writes only the latest draft, which is cheapest and what most people want; a flag replays every hosted version so history and version numbers match what people saw.

What this reuses: the storage helper already used for sponsor images, and the content proxy the viewer already reads from, which learns to serve h_ ids. The viewer does not change except for a badge that says "not on chain".

Cost lives here. A hosted single-file plan is kilobytes. A hosted folder with images is megabytes, and the same bytes again on every version until ORDFS directories exist. Free covers a handful of plans at the 5 MB limit; folders, more plans, and long histories are the paid tier. Numbers are in the pricing memo, not here.

Done when: a machine with no wallet and no BSV publishes a plan and shares a link that opens; the same plan is inscribed later and the old link still resolves.

5. Skill package

New repo · one day · no code changes

One SKILL.md installable with npx skills add opldotdev/bitplan-skill, laid out like the 1sat CLI skill. It lists the phrases an agent hears ("publish this plan", "share this with X", "put this on chain"), tells the agent to read bitplan.dev/llms.txt first and trust live CLI output over the skill text, wraps the CLI's --json mode, and spells out three rules: a wallet must be unlocked, a plan an agent reads enters its context, and no tool ever returns key material. Other editors get their manifests when someone asks.

Three questions answered

What is the 512 KB limit?

A number we copied from postplan. It is not a Bitcoin limit. Publishing costs about one satoshi per kilobyte, so a 5 MB plan would cost a few thousand satoshis, still cents. The real ceilings are the content proxy, which refuses envelopes over 640 KB, and how large a single transaction the relay accepts, which we have not tested past this size. Raising it to 5 MB means changing two constants and publishing one big test plan. 5 MB is the number: it fits a built app with images, and a 5 MB plan on chain still costs cents.

We are the odd one out with postplan, and for the same reason: a plan is a file someone else wrote, rendered inside our site. The worry is a poison plan. Someone shares a plan with you, you open it, and it does something to you.

What a poison plan could actually do, and what stops it:

  • Phone home. Report that you opened it, when, from where, and anything you typed into it. Scripts are stopped by denying the page network access. An image from a host the author controls can still report an open, and we accept that, because most plan images are on-chain assets on ORDFS gateways and the rest are a trade the author makes knowingly.
  • Fake a wallet prompt. Draw a convincing "enter your seed" box. Nothing technical stops a picture of a box. The defence is that the real wallet never asks inside the plan, and the viewer says so around the frame.
  • Reach the wallet or the site. Stopped already. The plan runs in a frame with no identity of its own, so it cannot see bitplan.dev cookies, storage, or the wallet connection.
  • Open windows or navigate you away. Stopped already by the frame's sandbox.

So the choice is not "scripts or safety". It is whether to allow scripts with the network shut. A page that can compute but cannot talk gives plans copy buttons, choices that build a reply, live tables, and small tools, and a poison plan still has nowhere to send anything. The way to do it is one policy line injected into every rendered plan that allows images and fonts from anywhere but denies scripts any network call. Two things to test first: that copy to clipboard works from inside a sandboxed frame, and that the injected policy holds in Safari as well as Chrome.

Do reader links expose key material?

No. The link secret is a fresh random key made for that plan. It is not derived from any wallet, and nothing about a wallet can be derived from it. A link holder gets the plan and nothing else.

Later, with issues already filed

  • A real origin per plan such as <origin>.plans.bitplan.dev with a service worker serving the decrypted bundle. That is what a compiled app with module imports and relative fetches needs, and what here.now and postplan do. Isolation then comes from the browser's origin model instead of the sandbox attribute.
  • ORDFS directories for plans, once 1sat-sdk #13 lands, so a new version references unchanged files instead of re-uploading them. Leaner drafts, not a requirement.
  • Headless agents that run with nobody present get their own wallet identity. The Secure Enclave part is small: the key already has no hardware lock, so "no fingerprint" is skipping one call. OPL-4324 and OPL-4325.
  • Billing for hosted drafts, only if they see use. OPL-4330.
  • Clearer errors when a publish is interrupted or two publishes race. OPL-4333.

Decisions

Pick one answer per question. Each option says what it means. The block at the end fills in as you choose. Copy it and paste it back to the agent.

1. Retire the private envelope

One format instead of two.

2. Reader links

A throwaway key in the link. No envelope change.

3. Hosted drafts

Who can publish a hosted draft, and how the server knows it is them.

4. What inscribe writes to the chain

Hosted versions have no transactions, so history exists only on our server until this runs.

5. Scripts inside plans

Rich plans versus poison plans. External images stay allowed either way.

6. Size limit

512 KB is postplan's number, not Bitcoin's.
