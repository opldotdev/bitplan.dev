BitPlan · design and sequence · draft 2 · 2026-09-02

Agent keys, link readers, hosted drafts

One design that lets a coding agent encrypt and publish without a person at the fingerprint reader, lets a reader open a plan without a wallet, and lets a plan start on our server and end on the chain. Concrete steps first.

Keep

External BRC-100 wallet, no keys in BitPlan, no cleartext mode, one origin per plan, coin holder publishes, reader keys decrypt.

Add

An agent identity with its own headless wallet, a vault access policy that needs no biometry, a link slot in the envelope, and a hosted draft that can be inscribed.

Do not add

Any path that copies the owner's seed into an agent. Any server that can read a plan. Any new verb we do not need.

1. The Secure Enclave question

The worry: keys should sit behind the Secure Enclave, but an agent runs while nobody is at the machine, so a Touch ID prompt per operation makes autonomy impossible.

Three facts settle this.

  1. The Enclave never signs for Bitcoin. It only holds P-256 keys. Our secp256k1 identity key is always decrypted into process memory before it signs or derives a shared secret. The Enclave protects the key at rest and binds it to this device. That is the whole benefit, and it is a real one: a copied vault directory is useless on another machine.
  2. Touch ID is currently a software gate, not a hardware one. In @1sat/wallet-mac the key is created with SecureEnclave.P256.KeyAgreement.PrivateKey() and no SecAccessControl flags. The prompt comes from an LAContext check in the Swift helper before it touches the key. So "no fingerprint for agents" is a policy switch in code we own, and "fingerprint really required for owners" needs hardware flags we have not set yet.
  3. Presence belongs at unseal, not per use. The desktop wallet already works this way: one Touch ID at unlock, then the root key stays in the Bun process and serves BRC-100 calls. An agent wallet is the same shape with the unlock step made optional.

The policy is chosen per secret when it is protected and stored in the vault entry metadata. It cannot be loosened afterwards; loosening means creating a new key.

What device does not protect against. Any process running as the logged-in user can ask the helper to unwrap an agent key. That is the trade for autonomy. The mitigation is not a prompt, it is scope: the agent key holds cents, holds only the plan coins it was delegated, and is never the owner's identity. If that scope is not acceptable for a given plan, do not delegate it.

2. Two identities, one envelope

Owner identity

  • 1Sat Wallet on desktop or phone. Touch ID or password at unlock.
  • Holds funds and, by default, every plan coin.
  • Always a reader slot in every envelope the agent publishes. The CLI refuses to publish otherwise.
  • Never exported. Never shared with an agent.

Agent identity

  • A separate headless BRC-100 wallet: @1sat/wallet-node plus @1sat/vault with the device policy on macOS.
  • Own identity key, own deposit address, own small balance.
  • Reads plans shared with it. Publishes only plans whose coin the owner delegated to it.
  • Serves BRC-100 on a second loopback port, or over the stdio bridge from the 1Sat CLI wallet plan.

Nothing in the envelope changes for this. A shared envelope already wraps one document key per reader identity. The agent is one more reader. Publishing authority is already "whoever holds the coin". Delegation is a coin transfer.

Delegation and revocation

EnrollOwner runs bitplan contacts add agent <key> and funds the agent address from the phone. One QR.
Sharebitplan upload plan.html --share-with agent. Agent can now read.
Delegatebitplan delegate <origin> --to agent. Owner wallet sends the 1-sat plan coin to the agent identity. No reinscription, origin and type tags stay.
WorkAgent runs bitplan upload plan.html unattended. Its wallet encrypts, signs, pays, reinscribes. Owner slot is mandatory.
Reclaimbitplan reclaim <origin> tells the agent wallet to send the coin back. Or the owner forks to a new origin if the machine is gone.

Honest limit: if the agent machine is lost or compromised while it holds a plan coin, the owner cannot take that origin back. The owner can still read every version, and a fork costs one publish. Plans are cheap by design, so this is the accepted failure mode. Do not delegate coins for plans where the origin itself is the valuable thing.

Why not owner-wallet auto-approval instead

The alternative is to keep the coin in the owner wallet and let a paired agent reuse a saved permission to spend bitplan coins under a cap. That is the better long-term shape and it is what BRC-116 describes. It is blocked today: BSV Desktop and 1Sat Wallet accept a caller-supplied Originator header, so any local process can inherit a saved grant. Until wallets authenticate native callers, a separate agent identity with its own tiny balance is the honest design. When authenticated originators land, delegation can become a wallet grant instead of a coin transfer, and nothing in BitPlan's envelope or CLI surface has to change.

3. Readers without a wallet: the link slot

Every product on the compare page can hand a reader a link. We cannot. This is the largest usability gap and it needs no server.

Add a slot kind to the shared envelope whose wrap key comes from a secret carried in the URL fragment. Browsers never send the fragment to the server, so bitplan.dev, the chain, and ORDFS all see ciphertext only.

{
  "v": 3,
  "key": {
    "mode": "brc2-multi",
    "protocolID": [2, "bitplan"],
    "keyID": "<per-draft UUID>",
    "payloadLength": 1282,
    "senderIdentityKey": "<compressed public key>",
    "slots": [
      { "kind": "identity", "identityKey": "<sender>", "offset": 1282, "length": 80 },
      { "kind": "link", "kdf": "hkdf-sha256", "offset": 1362, "length": 60 }
    ]
  }
}

wrapKey  = HKDF-SHA256(ikm = fragmentSecret, salt = keyID, info = "bitplan-link-v1", 32 bytes)
slotBody = SymmetricKey(wrapKey).encrypt(documentKey)
URL      = https://bitplan.dev/d/<origin>#k=<base64url(fragmentSecret)>
  • Bump the envelope version byte to 0x03. Readers reject unknown versions today, which is exactly the behaviour we want for a slot they cannot parse. Existing v1 and v2 readers are untouched.
  • The fragment secret is 32 random bytes from the OS CSPRNG, generated by the CLI, printed once, and stored in ~/.bitplan/drafts.json beside the origin so bitplan upload can keep the same link on the next version.
  • bitplan upload plan.html --link adds the slot. --private already drops shared readers on the next version and will drop the link slot too. Rotating a leaked link is one publish.
  • The viewer reads location.hash, derives the wrap key in the browser, and never puts the secret in a request, a cookie, or storage. The header hash binding already covers the new slot, so a tampered slot list is rejected.
  • A link reader is anyone with the link. Say that plainly in the CLI output. Identity slots remain the choice for named readers.

4. Hosted drafts and inscribe

Same envelope, same wallet keys, different storage. The verb for moving a hosted draft to the chain is inscribe. "Promote" implied a hierarchy we do not want to explain. Inscribe is what actually happens.

bitplan upload plan.html --hosted       # ciphertext stored by bitplan.dev, id h_xxxx
bitplan upload plan.html                # same file again: new hosted version
bitplan inscribe h_xxxx                 # latest envelope goes on chain; h_xxxx redirects to /d/<origin>
  • Writes are BRC-100 signed requests. The identity key is the account. No email, no password, no session.
  • Blobs are content-addressed by SHA-256 of the envelope. Each version hash is signed by the publisher, and the viewer verifies it, so the server cannot substitute a version.
  • If-Match on the current version hash gives the same conflict safety the chain gives for free.
  • A hosted draft leaks less than a chain draft: the reader list in the header is visible only to our server. Say so on the pricing page.
  • Free tier first, no billing. Billing, terms, and a privacy policy are step five and mostly not engineering.

5. Sequence

Ordered by how little they depend on anything else. Each step ships on its own and is useful on its own.

Step 1 Vault access policy · 1sat-sdk · about a day

Add access: 'biometry' | 'device' | 'session' to protectSecret in @1sat/vault. In wallet-mac, create biometry keys with real SecAccessControl flags and skip the LAContext check for device. Record the policy in the vault entry.

Done when: a device secret unwraps in a headless process with no prompt, a biometry secret refuses to unwrap without Touch ID even if the helper's software check is bypassed, and the vault CLI shows the policy of every entry.

Step 2 Agent wallet daemon · 1sat-sdk · two to three days

1sat agent start creates or opens a wallet-node account whose root key is vault-protected with the device policy, prints its identity key and a deposit QR once, and serves BRC-100 on a second loopback port. Reuse the stdio bridge from the 1Sat CLI wallet plan if it exists by then. Originator is fixed to the calling tool, and only wallet methods are exposed.

Done when: bitplan auth --wallet-url http://127.0.0.1:3322 succeeds with nobody at the keyboard, and the daemon survives a logout and login without a prompt.

Step 3 Delegate and reclaim · bitplan CLI · two days

bitplan delegate <origin> --to <contact> transfers the plan coin without reinscribing. bitplan reclaim <origin> asks the wallet that holds it to send it back to the owner identity recorded in the draft map. The CLI adds the owner identity as a mandatory reader slot whenever the publishing wallet is not the owner, using an owner field in drafts.json and the address book.

Done when: an owner delegates a plan, an agent publishes two versions unattended, the owner reads both from the phone, and reclaim returns the coin.

Step 4 Link slot · bitplan CLI and viewer · three days

Envelope v3 with the link slot kind, --link on upload, fragment handling in the viewer, and a compatibility test that opens CLI-produced v3 envelopes in the web implementation.

Done when: a plan opens in a private browser window from the link alone, the same URL still opens the next version, and --private makes it stop working.

Step 5 Agent skill package · half a day

Publish a skill that npx skills add opldotdev/bitplan installs, wrapping the CLI's JSON mode. This is how here.now got adopted inside agent frameworks. Ours already has the JSON surface; it only lacks the package.

Step 6 Hosted drafts and inscribe · web and CLI · a week

Signed-request auth, content-addressed blob storage, signed version lists, the /h/<id> viewer route with a visible "not on chain" badge, and inscribe. Free tier, no billing.

Step 7 Billing and terms

Only if step 6 sees use. Card via Stripe, or BSV via the sponsor payment path. Needs an entity, terms, and a privacy policy that covers stored ciphertext.

6. Corrections to earlier notes

  • --description and --new already exist on bitplan upload. They were listed as gaps in the hosted tier memo. They are not.
  • Concurrent-publish safety is already real: the second reinscription fails because the coin is spent. The only work is a clearer CLI error and a line in the docs.
