BitPlan · design and sequence · draft 3 · 2026-09-02

Agent keys, link readers, hosted drafts

Agents use the human's wallet. Headless agents get their own. Readers get a link. Plans can start on our server and end on the chain. Concrete steps first.

What changed since draft 2

  • Agents no longer get their own identity by default. A person driving an agent uses that person's wallet. Separate agent identities are for headless, orchestrated runs only.
  • Delegation by coin transfer is dropped as an agent mechanism. Transfer stays as a handoff to another human.
  • BRC-116 is explained where it is used.
  • Hosted drafts are a likely go and gain a no-wallet mode option. The unstable-origin consequence of inscribing later is spelled out.
  • The agent daemon builds on the existing 1sat serve and @1sat/wallet-node rather than a new program.
  • The skill package is modelled on here.now's, which has been polished over 114 commits.
  • Sequence reordered: the three steps that need no wallet work come first.

Keep

External BRC-100 wallet, no keys in BitPlan, no cleartext mode, one origin per plan, coin holder publishes, reader keys decrypt.

Add

A skill package, a link slot in the envelope, hosted drafts with inscribe, a vault policy for headless agents, and transfer to another person.

Do not add

Any path that copies a seed into an agent. Any server that can read a plan. A second identity for a person who is already at the keyboard.

1. Whose identity does an agent use?

Person at the keyboard

  • The agent calls the person's wallet: BSV Desktop or 1Sat Wallet on this machine, unlocked once with Touch ID or a password.
  • Plans are encrypted to the person's identity. Sharing means adding people, never adding an agent key.
  • The wallet's saved permissions for the bitplan.dev originator decide how often it prompts. Auto-lock is the safety knob.
  • Nothing to enroll, nothing to fund, nothing extra to lose.

Headless or orchestrated run

  • No person is present, so the run gets its own identity: a @1sat/wallet-node account behind 1sat serve, root key vault-protected with the device policy on macOS.
  • Treated like a team member: plans are shared to it with --share-with, and it holds only the coins for plans it created.
  • Own tiny balance. Never the person's identity.

This removes the enrol, fund, delegate, and reclaim ceremony from the normal path. It also removes the failure mode where plans end up in an agent's wallet and get lost. The envelope does not change in either case.

Transfer to another person

bitplan transfer <origin> --to <contact> sends the 1-sat plan coin to another identity without reinscribing. Origin and type tags stay, per BRC-147. Ownership of future versions changes hands. The previous owner keeps read access to every version already published, because those envelopes already hold their reader slot. This is a handoff, not a delegation, and it is a clear one.

Why the per-use prompt is a wallet setting, and what BRC-116 is

BRC-116, "Wallet Permissions and Counterparty Trust", is the normative spec for how a BRC-100 wallet handles application permissions: how an app is identified by its originator domain, how grants are requested, persisted as encrypted permission tokens, renewed, and revoked, and how security levels 0, 1, and 2 decide whether a prompt is per app or per counterparty. It is why BSV Desktop can remember that bitplan.dev may use the [2, "bitplan"] protocol and stop asking.

It also carries a security note: the wallet, browser, and operating system are expected to confirm that an originator is authentic. BSV Desktop 2.8.3 and the 1Sat desktop wallet read a caller-supplied Originator header for native callers, so any local process can claim bitplan.dev and inherit its saved grants. That is the upstream issue drafted in docs/bsv-desktop-origin-authentication-issue-draft.md. Until wallets authenticate native callers, saved grants on the person's wallet are convenient but not a security boundary. Auto-lock is.

2. The Secure Enclave question, for headless agents

  1. The Enclave never signs for Bitcoin. It holds P-256 keys only. The secp256k1 identity key is decrypted into process memory before it signs or derives a shared secret. The Enclave protects the key at rest and binds it to this device. A copied vault directory is useless elsewhere.
  2. Touch ID is currently a software gate. @1sat/wallet-mac creates the key with SecureEnclave.P256.KeyAgreement.PrivateKey() and no SecAccessControl flags. The prompt is an LAContext check in the Swift helper. So "no fingerprint for headless agents" is a policy switch, and "fingerprint really required for owners" needs hardware flags that are not set yet.
  3. Presence belongs at unseal, not per use. The desktop wallet already works that way: one Touch ID at unlock, then the root key stays in the Bun process. A headless agent is the same shape with the unlock step made optional.

3. Readers without a wallet: the link slot

Every product on the compare page can hand a reader a link. We cannot. Today's viewer also cannot reach a wallet from inside some embedded browsers at all, including the one in the Claude desktop app, which blocks every request to localhost. A link slot decrypts from the URL fragment inside the page, with no wallet call, so it works there too.

{
  "v": 3,
  "key": {
    "mode": "brc2-multi",
    "protocolID": [2, "bitplan"],
    "keyID": "<per-draft UUID>",
    "payloadLength": 1282,
    "senderIdentityKey": "<compressed public key>",
    "slots": [
      { "kind": "identity", "identityKey": "<sender>", "offset": 1282, "length": 80 },
      { "kind": "link", "kdf": "hkdf-sha256", "offset": 1362, "length": 60 }
    ]
  }
}

wrapKey  = HKDF-SHA256(ikm = fragmentSecret, salt = keyID, info = "bitplan-link-v1", 32 bytes)
slotBody = SymmetricKey(wrapKey).encrypt(documentKey)
URL      = https://bitplan.dev/d/<origin>#k=<base64url(fragmentSecret)>
  • Envelope version byte 0x03. Readers reject unknown versions, which is what we want for a slot they cannot parse. v1 and v2 readers are untouched.
  • The 32-byte secret comes from the OS CSPRNG, is printed once, and is stored in ~/.bitplan/drafts.json so the next version keeps the same link. --private drops it. Rotating a leaked link is one publish.
  • The viewer reads location.hash, derives the wrap key in the browser, and never puts the secret in a request, cookie, or storage. The header hash binding covers the new slot.
  • A link reader is anyone with the link. The CLI says so when it prints one. Identity slots remain the choice for named readers.

4. Hosted drafts and inscribe

Same envelope, stored by bitplan.dev instead of the chain, moved to the chain with bitplan inscribe. This opens BitPlan to people with no BSV, which is most people, so it is a likely go.

bitplan upload plan.html --hosted       # ciphertext stored by bitplan.dev, id h_xxxx
bitplan upload plan.html                # same file again: new hosted version
bitplan inscribe h_xxxx                 # goes on chain; h_xxxx redirects to /d/<origin>
  • Writes are BRC-100 signed requests. The identity key is the account. No email, no password.
  • Blobs are content-addressed by SHA-256 of the envelope. Each version hash is signed by the publisher and verified by the viewer, so the server cannot substitute a version.
  • If-Match on the current version hash gives the conflict safety the chain gives for free.
  • A hosted draft leaks less than a chain draft: the reader list in the header is visible only to our server.
The origin is not stable until inscribe. Hosted versions are not transactions. There are no inputs, so there is no txid and no outpoint until inscribe runs, and the origin minted then cannot be predicted from the hosted id. Consequences: the hosted URL must keep working as a redirect forever, anything that recorded h_xxxx (a PR description, a drafts map, a share) must resolve through us, and the version numbers people saw while hosted must line up with what lands on chain. Question 5 below decides whether inscribe writes only the latest version or replays every hosted version as a reinscription chain so history lands too.

No-wallet mode

Hosted plus the link slot makes a mode with no wallet at all possible: the CLI generates the document key and the link secret locally, wraps the key with the link slot only, and authenticates to the server with a publisher token it stores in ~/.bitplan. Nothing on the machine holds a Bitcoin key. Anyone can run npx bitplan upload plan.html and get a private link in one command, exactly like postplan and here.now, except the server sees ciphertext. When a wallet appears later, the next version adds an identity slot and the draft can be inscribed. Question 4 asks whether to build this.

5. Agent skill package

here.now's skill is the model. What they got right after 114 commits, and what we copy:

  • Frontmatter description that lists the trigger phrases an agent will hear: "publish this", "share this plan", "make this private", "who can read this". Ours add "put this on chain", "give X access", "read the plan".
  • A skill version line and a "read the current docs first" rule pointing at a machine-readable source. We already serve /llms.txt and /openapi.json; the skill points there and says to trust live CLI output over local text.
  • One layout published to several hosts: skills/bitplan/SKILL.md, a Hermes path, .codex-plugin and .cursor-plugin manifests, plus a well-known endpoint at https://bitplan.dev/.well-known/skills/bitplan.
  • Helper scripts as thin wrappers over the public interface, with an explicit "if the scripts are missing, call the interface directly" section. Ours wrap npx bitplan ... --json.
  • Stale-base guidance written for the agent: what a conflict looks like and what to offer the user. Ours is the spent-coin error.
  • What we add that they do not need: the wallet requirement, the plaintext boundary once an agent reads a plan, and the rule that no tool returns or accepts key material.

6. Sequence

Ordered by how little each step depends on anything else. The first three need no wallet changes.

Step 1 Skill package · bitplan repo · one day

Repository opldotdev/bitplan-skill laid out like here.now's, installable with npx skills add opldotdev/bitplan-skill --skill bitplan -g, with the well-known endpoint served by bitplan.dev.

Done when: a fresh Claude Code, Codex, or Cursor session with the skill installed can list, read, and publish a plan through the CLI with the wallet unlocked, and correctly refuses to return key material.

Step 2 Link slot · bitplan CLI and viewer · three days

Envelope v3, --link on upload, fragment handling in the viewer, compat test opening CLI-produced v3 envelopes in the web implementation.

Done when: a plan opens in a private window and in the Claude desktop embedded browser from the link alone, the same URL opens the next version, and --private makes it stop working.

Step 3 Hosted drafts and inscribe · web and CLI · a week

Signed-request auth, content-addressed blobs, signed version list, /h/<id> route with a visible "not on chain" badge, inscribe, permanent redirect after inscribe. No-wallet mode if question 4 says yes. Free tier, no billing.

Done when: a machine with no wallet and no BSV publishes a plan and shares a link that opens; the same plan is inscribed later and the old link still resolves.

Step 4 Vault access policy · 1sat-sdk · about a day

access: 'biometry' | 'session' | 'device' on protectSecret. Hardware flags for biometry. Skip the LAContext check for device.

Step 5 Headless wallet mode in 1sat serve · 1sat-sdk · two to three days

1sat serve already wraps the same createNodeWallet instance the CLI uses and exposes storage RPC. Add a mode that serves the BRC-100 JSON API the way BSV Desktop does on 3321, on a second loopback port, with the originator fixed to the calling tool and only wallet methods exposed. Root key vault-protected with the policy from step 4.

Done when: bitplan auth --wallet-url http://127.0.0.1:3322 succeeds with nobody at the keyboard and the daemon survives logout and login.

Step 6 Transfer to another person · bitplan CLI · one day

bitplan transfer <origin> --to <contact>. Coin moves, origin stays, previous owner keeps read access to existing versions.

Step 7 Billing and terms

Only if hosted drafts see use. Card via Stripe or BSV via the sponsor payment path, about $5 a month. Needs an entity, terms, and a privacy policy covering stored ciphertext.
