High-level product and engineering plan · 2026-08-30

BitPlan everywhere, without passing around a mnemonic

Make BitPlan useful where plans are written—coding agents and desktop environments—while keeping mobile review effortless and keeping root keys inside a real BRC-100 wallet.

The outcome

A person can create or review a plan on a phone, continue working with it on a desktop, and authorize a coding agent to read or update it. None of those workflows should require copying the owner's mnemonic into the application or agent environment.

Plan
Encrypted and versioned by BitPlan
Wallet
Owns keys, permissions, and publishing authority
Agent
Reads only the plans it is allowed to use
Mobile
Reviews and approves without becoming a key courier

Decisions already made

  • BitPlan will remain a BRC-100 application and will not embed an owner wallet.
  • The normal workflow will not copy the owner's mnemonic into an agent.
  • Publishing control and reading access remain separate capabilities.
  • The product name is 1Sat Wallet, covering mobile and desktop.
  • BSV Desktop is not our implementation project. We will report focused interoperability or security issues upstream when needed.
  • MCP is useful agent ergonomics, but it is not required to create or use a BitPlan. The existing CLI is the first working agent interface.

What works today

CLI wallet access

The BitPlan CLI already connects to a local BRC-100 wallet, encrypts plans, publishes versions, lists owned plans, and decrypts a known plan.

Mobile reading

BitPlan already connects inside BSV Browser because that browser supplies an injected BRC-100 wallet.

Shared readers

Envelope v2 wraps one document key for the owner and each invited identity, so readers do not need the owner's mnemonic.

Separate authority

The current 1-sat plan coin authorizes the next version. A reader identity does not automatically receive publishing authority.

The gaps

  1. Agent ergonomics: agents can run the CLI, but typed and narrowly scoped tools would be safer and easier to discover.
  2. Shared-plan discovery: a recipient can decrypt a known origin but cannot automatically list everything shared with it.
  3. Device enrollment: adding a desktop or agent reader still needs a clear pairing and approval ceremony.
  4. Wallet availability: 1Sat Wallet does not yet expose the full BRC-100 interface to external desktop applications.
  5. Origin authentication: saved application permissions are only safe when the wallet can authenticate the requesting application.
  6. Plaintext boundary: once an agent reads a plan, that plan enters the agent's model context. The product must make that explicit.

BitPlan workstreams

1. Dogfood the existing CLI

Use the CLI now for agent-created plans. Improve its JSON outputs and non-interactive behavior only where real agent use reveals friction. This provides value before any new protocol or connector exists.

2. Add a local BitPlan MCP server

Wrap BitPlan's existing library and BRC-100 client in focused tools such as list_plans, read_plan, prepare_update, and publish_plan. Do not expose a raw wallet proxy or mnemonic tools. Publishing remains a separate, reviewable operation.

3. Build an encrypted “shared with me” index

Store plan origins, current versions, encrypted metadata, and membership in a discoverable index. A server or overlay may host ciphertext, but it should not learn plan contents. This closes the largest current product gap for secondary devices and agent identities.

4. Add device and agent roles

Let an owner approve a separate device or agent identity as a reader. Keep roles explicit: reader, editor that prepares local changes, and publisher that can use the plan coin. Default agents to reader/editor, not owner.

5. Improve future revocation and privacy

Rotate keys for future versions when a member is removed and investigate a later envelope format that leaks less recipient metadata. Be honest that an immutable older version, or plaintext already read by an agent, cannot be taken back.

Wallet work delegated to 1Sat Wallet

  • One transport-independent dispatcher for the complete BRC-100 interface.
  • BRC-116-aligned permissions with authenticated originators.
  • A QR-paired encrypted phone-to-desktop wallet session.
  • A macOS target that can serve desktop applications without exporting the seed.
  • Stable identity derivation and wallet-state migration or synchronization.
  • An end-to-end BitPlan acceptance test using the real CLI or BitPlan library.

Publishing policy for agents

  • Reading access can be persistent and plan-scoped.
  • Edits are prepared as local files with a visible diff.
  • Publishing shows the origin, next version, content hash, recipients, and estimated cost.
  • The wallet holding the plan coin approves or grants the publishing action.
  • Every agent read and publish attempt is auditable.
  • No tool returns or accepts a mnemonic, WIF, or raw root private key.

Success looks like

  1. A coding agent lists and reads approved plans through a wallet without seeing its mnemonic.
  2. The same plan appears on mobile for review and on desktop for implementation.
  3. A newly paired device discovers plans shared with it without receiving origin links manually.
  4. An agent can prepare a new version, while publication remains an explicit wallet-controlled step.
  5. Removing a device prevents access to future versions after key rotation.
  6. BitPlan works with multiple conforming BRC-100 wallets rather than depending on one vendor.

Recommended sequence

  1. Use and refine the CLI immediately.
  2. Add the local MCP server as a small adapter over existing BitPlan code.
  3. Design and implement the encrypted shared-plan index.
  4. Add device and agent enrollment to BitPlan.
  5. Integrate the general BRC-100 transport delivered by 1Sat Wallet.
  6. Iterate on privacy, revocation, and unattended-agent policy from real use.

Open questions

  • Should the encrypted shared-plan index live in an overlay, a conventional service, or both?
  • Should agent access use a dedicated local identity, a remote phone wallet, or a selectable combination?
  • Which plan sections may an agent read by default, and which require an additional approval?
  • When should BitPlan introduce a v3 envelope rather than extending the v2 index around it?
  • What level of publishing autonomy is useful without weakening the human-controlled plan coin?
