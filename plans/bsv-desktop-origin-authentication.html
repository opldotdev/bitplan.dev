Authenticate native BRC-100 callers before reusing saved permissions

BSV Desktop correctly exposes the standard BRC-100 methods. The concern is narrower: a native application identifies itself with a caller-supplied Originator header, so another local process can claim the same application domain.

Why this matters

BRC-100 permissions are scoped to an application originator. After a user saves a permission for one application, a separate local process may be able to present the same domain and ask the wallet to reuse that permission.

The wallet lock and permission prompts still provide useful protection. This is not a claim that keys are exposed or that every forged request will succeed automatically.

What the standard expects

BRC-116 says the wallet, browser, operating system, or communication substrate is expected to confirm that an originator is authentic and prevent forged requests. Browser-managed Origin headers help with web applications. A caller-controlled native header does not identify one local application from another.

Expected behavior

BSV Desktop should reuse saved permissions only when it can verify that the request came from the application to which those permissions were granted.

Possible direction

Keep the existing BRC-5 endpoints for compatibility, but distinguish verified and unverified native callers. The maintainers could:

  • Pair a native application once and issue it a local credential.
  • Bind that credential to the approved originator.
  • Authenticate later calls with mTLS, signed challenges, or trusted operating-system IPC.
  • Reuse persistent permissions only on an authenticated channel.
  • Prompt, use an ephemeral grant, or reject sensitive calls from an unverified header.

The important property is simple: copying an application's domain string should not copy its saved wallet permissions.

Safe verification

  1. Use an unfunded test wallet profile.
  2. Grant a harmless protocol permission to a test native application.
  3. Make the original request through that process.
  4. Start a different process with no pairing or application credential.
  5. Send the same request with the same Originator value.
  6. Check whether the second process receives the saved permission.

What this report is not asking for

  • It does not ask BSV Desktop to remove BRC-5 or its local API.
  • It does not claim the 28 BRC-100 methods are missing.
  • It does not ask for removal of BSV Desktop's additional token APIs.
  • It does not prescribe one cross-platform authentication technology.

Before submitting an issue

  • Ask whether another authentication layer exists outside the inspected HTTP path.
  • Reproduce only with a harmless permission and a test wallet.
  • Let the BSV Desktop maintainers choose severity and implementation.
  • Keep the issue focused on origin authentication and saved permission reuse.
