Decision made

Sigma will not support legacy xprv backups or pre-0.3 compatibility paths. There are no legacy Sigma users to migrate, so those branches are dead weight rather than compatibility.

The restore rule

Current Sigma backup
Restore the supported key container.
→
Exact profile match
Compare with profile.member_pubkey.
→
Sign in
No key writes, rotation, migration, or chain action.
Anything else stops clearly.

An old format, missing profile binding, or mismatched key returns a plain unsupported-or-mismatch error. It never guesses, falls back, rewrites the account, or redirects into another password prompt.

What gets removed

Runtime paths

  • Legacy xprv restore and format detection.
  • Pre-0.3 identity metadata reissue.
  • user.pubkey as a fallback profile locator.
  • Fallback key derivation and automatic conversion.

Maintenance weight

  • Legacy fixtures and compatibility tests.
  • Documentation that suggests old backups work.
  • Branches that preserve currentPath only for legacy reissue.
  • Ambiguous errors that invite another fallback.

Implementation steps

1. Prove the assumption without adding compatibility

Sigma data · read-only · before deployment

Run a one-time count of profiles that would require a legacy path. Zero is expected. If it is not zero, stop and inspect the records; do not restore the fallback.

2. Delete legacy restore code

sigma-auth · authentication and restore modules

Remove old-format detection, xprv loading, metadata reissue, user-level lookup fallback, and conversion branches. Keep only the current restore entry point.

3. Make authority profile-first

sigma-auth · restore verification

Verify the proof, load the selected profile, and require an exact match with profile.member_pubkey. A mismatch performs zero writes.

4. Replace compatibility tests with boundary tests

sigma-auth · focused test suite

Test the current backup success path, wrong-key rejection, unsupported legacy input, zero-write failure behavior, and navigation only after success.

5. Say exactly what Sigma supports

restore screen and documentation

Describe the current Sigma backup format plainly. Remove promises of automatic migration. Tell someone with an unsupported file that it cannot be restored.

Protocol boundaries

  • BRC-100 is the wallet interface Sigma uses for wallet operations. It is not an inscription or backup format.
  • BAP identity and operational key rotation remain separate from routine Sigma restore.
  • BitPlan hosted draft means this encrypted plan is stored off-chain temporarily. It becomes a 1Sat Ordinal only if someone later chooses to inscribe it.

Done when

  • Only the current Sigma backup format can enter restore.
  • The restored key must exactly match the selected profile.
  • Legacy inputs fail with one clear message.
  • No fallback, migration, account rewrite, key rotation, or on-chain action remains.
  • The current backup succeeds on another device without changing identity.
